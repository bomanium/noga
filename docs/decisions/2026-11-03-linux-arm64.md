# A Linux arm64 release

Asked 2026-11-03, after HTTPS for a shared server, with the backlog's Maybe ideas as the choices: a release of
0.1.0-alpha.3, **Linux arm64 releases**, signing and macOS, or the AVC patent check.

**Answer: Linux arm64 releases.** The option said CI could cross-publish them but not run them without an arm64
runner (paid minutes on a private repository).

## What was built

- `FrameReader.Native.linux-arm64` (2.21.0, the same FFmpeg build options as linux-x64: no `--enable-gpl`, no
  `--enable-nonfree`) referenced beside linux-x64 and win-x64; SkiaSharp and HarfBuzzSharp already carry linux-arm64.
- `tools/publish.sh` builds linux-arm64 by default: the folder, its `.tar.gz` and `mediaqc-VERSION-aarch64.AppImage`
  (type2-runtime's runtime-aarch64, pinned by SHA-256 like the x86_64 one, with the same licences).
- Running it without an arm64 runner: `tools/arm64-check.sh` runs the release on x64 under qemu-user,
  `qemu-aarch64-static -L` with Ubuntu 24.04's arm64 base image (pinned by SHA-256) for glibc and libstdc++, which
  needs no binfmt handler (the cloud sessions' sandbox has none). It unpacks the AppImage with its own runtime and runs
  the command inside, then checks samples with the arm64 folder and the x64 one and requires the same exit code and
  the same findings (check, severity, value, message). CI runs it on the ProRes and H.264 samples, the FFmpeg path and
  the managed one. On 2026-11-03 all five of make-samples.sh's files gave the same 87 findings on both.
- Tiered compilation is off under emulation (`DOTNET_TieredCompilation=0`): with it on, every check crashed under
  qemu-user with SIGSEGV at a random point, from .NET patching code it is running (tier-up), which qemu's translated
  code doesn't follow; `--version` and `--help` ran either way. On ARM hardware the default stays.
- Not run on ARM hardware: the desktop app (Avalonia, X11) under emulation isn't tried; one run on a Raspberry Pi or an
  ARM machine would settle it before a stable release.
